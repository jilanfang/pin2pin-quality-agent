# LLM 使用策略

本文档定义当前 `8D Copilot` 的 LLM 使用边界、模型分层和升级规则，目标是：

- 降低调用成本
- 保持关键推理质量
- 避免所有环节都依赖顶级大模型

## 1. 总原则

不是所有步骤都需要最强模型。

当前采用的默认策略更新为：

`前两档统一走 qwen3.5-plus -> 第三档默认走 DeepSeek 普通模式 -> 复杂高价值推理再升级到 deepseek-reasoner`

判断标准不是“能不能用大模型”，而是：

- 这个任务能否规则化
- 这个任务是否高频
- 这个任务是否真的需要复杂推理
- 这个任务失败的代价有多高

---

## 2. 当前分层使用策略

## 2.1 第 0 层：规则与校验层

这层不是“纯规则抽取”，而是“规则负责确定性部分”。

适用场景：

- 阶段流转
- `confirm / unlock / revalidate`
- report gating
- `open / closed`
- 导出权限控制
- HTML / 文本 / PDF 渲染
- 模型输出后的字段校验与归一化
  - 日期标准化
  - 批次格式清洗
  - 工单号格式归一
  - 料号规范化
  - 枚举状态落盘

原因：

- 这类任务需要稳定、确定、可重复
- 适合由代码收口，不适合完全交给模型自由发挥

注意：

- 用户输入里的 `日期 / 批次 / 工单号 / 客户名 / 料号 / 阶段状态` 不应只靠规则抽取
- 这些字段虽然“看起来结构化”，但在真实客诉和工程语境里，经常被埋在口语、缩写、暗指、上下文引用里
- 因此更合理的方式是：
  - 先让 `qwen3.5-plus` 做广覆盖抽取
  - 再由规则做校验、归一化、去重和格式化

## 2.2 第 1 层：默认入口层（`qwen3.5-plus`）

适合高频、轻中度推理、语言整理和一轮广覆盖抽取类任务。

适用场景：

- 对所有用户输入做第一轮信息提取
- 从零碎口语里抽取潜在结构化字段：
  - 日期
  - 批次
  - 工单
  - 客户
  - 料号
  - 产品型号
  - 站点
  - 线体
- 判断一句话更像：
  - 事实
  - 假设
  - 风险
  - 待补信息
- 把用户零碎输入整理成更清晰的话
- 生成下一轮追问
- 文风改写
- 把阶段草稿润色得更易读

默认模型：

- `qwen3.5-plus`

特点：

- 调用频率最高
- 默认成为“所有用户输入”的第一道语义入口
- 同时承担轻量整理和中等复杂度分析
- 当前阶段为了简化路由，不再额外拆一个更低档文本模型

## 2.3 第 2 层：默认主分析层（仍使用 `qwen3.5-plus`）

这是当前阶段的主力分析层，但模型仍和第一层保持一致。

适用场景：

- 从多轮碎片输入中抽取结构化事实
- 识别前后矛盾
- 识别“后续信息推翻前序判断”
- 生成 D2 / D3 / D4 阶段工作稿
- 输出 `guided thinking`
- 对 benchmark case 做质量对齐和评测

默认模型：

- `qwen3.5-plus`

特点：

- 对质量要求高于轻改写
- 当前实现上不再为了“形式上的三档”额外切模型
- 好处是 prompt、评测和 fallback 逻辑更简单
- 适合先把主流程跑稳

## 2.4 第 3 层：高级模型层（默认 `DeepSeek`）

用于高价值、低频、较重推理任务。

适用场景：

- D4 根因分析中的复杂因果推理
- 同时存在多个假设时的证据权衡
- 区分发生原因、逃逸原因、系统原因
- 高质量 Final 报告润色
- 专家模式解释：
  - 为什么这样判断
  - 还缺什么证据
  - 下一步最有效的取证动作是什么

默认模型：

- `deepseek-chat`

复杂升级模型：

- `deepseek-reasoner`

特点：

- 第三档默认不再直接上 reasoning
- 先走 `deepseek-chat`
- 只有复杂度明显升高时才升级到 `deepseek-reasoner`
- 这样可以兼顾速度与推理质量

---

## 3. 建议的默认调用路径

对于一次正常案件处理，默认路径应该是：

1. 所有用户输入先交给 `qwen3.5-plus` 做一轮广覆盖抽取
2. 再由规则做字段校验、归一化、去重和状态更新
3. 阶段草稿、冲突识别和一般分析仍默认交给 `qwen3.5-plus`
4. 第三档任务默认走 `deepseek-chat`
5. 只有复杂根因推理或高风险 Final 场景时，再升级到 `deepseek-reasoner`

这意味着：

- 大多数会话不需要全程使用顶级模型
- 但绝大多数用户输入，仍值得先经过一个便宜模型
- 只有少数高复杂度章节需要升级

---

## 4. 何时升级模型

建议设置显式升级条件。

### 从规则层进入 `qwen3.5-plus`

触发条件：

- 只要用户输入了新的文本证据，就默认进入这一层

说明：

- 当前策略下，第一档和第二档不再区分模型
- 因此这里不再单独设计 “cheap -> mid” 升级逻辑

### 从 `qwen3.5-plus` 升级到 `deepseek-chat`

触发条件：

- 已经进入 D4 的实质分析阶段
- 用户输入明显碎片化且跨多轮
- 出现前后矛盾
- 缺失字段较多
- 用户输入中包含多个证据来源
- 需要生成更完整的阶段工作稿

### 从 `deepseek-chat` 升级到 `deepseek-reasoner`

触发条件：

- 根因路径超过 2 条且互相竞争
- 同时涉及发生原因与逃逸原因
- 证据不足但需要给出稳健判断框架
- 用户主动要求“深度分析”
- 用户要高质量 `Final` 对客稿
- 风险等级高，可能涉及停线、冒烟、起火、重大客诉

---

## 5. 在当前产品中的建议落点

结合现阶段 demo，建议这样分配：

### 当前就可以先不让 LLM 决定的部分

- 工作流引擎
- 出稿门槛
- 案件状态管理
- 报告渲染

### 第一批接 LLM 的部分（默认 `qwen3.5-plus`）

- `extractor` 的默认输入解析
- `guided-thinking` 的追问生成
- 阶段草稿生成
- 文风改写

### 第二批接 `DeepSeek` 的部分

- D4 深入分析
- Final 对客稿
- 专家解释模式

### `deepseek-reasoner` 只在复杂场景触发的部分

- D4 高质量根因分析
- Final 对客报告润色
- 专家解释模式

## 6. 成本控制建议

为了防止成本失控，建议加入以下机制。

### 6.1 分阶段调用

不要每次用户输入都全量重跑整案分析。

应优先：

- 增量分析当前输入
- 只重算受影响阶段

### 6.2 预检查再调用

在真正调用中高档模型前先做规则判断：

- 是否只是确认阶段
- 是否只是状态修改
- 是否只是导出动作

但对于新的用户输入文本，本策略默认仍建议至少经过一次 `qwen3.5-plus` 抽取。

### 6.3 Final 单独计费思路

未来如果商业化，可以把：

- 日常工作稿
- Final 高质量报告润色

拆成不同成本层。

因为真正贵的是 `deepseek-reasoner` 级别的复杂推理和高质量交付，不是基础整理。

---

## 7. 当前技术建议

当前阶段推荐的实现顺序：

1. 在领域层之外增加一个 `LLM tasks` 映射层
2. 把任务分成：
   - `rewrite`
   - `classify`
   - `extract`
   - `guided_question`
   - `draft_stage`
   - `root_cause_deep_analysis`
   - `final_polish`
3. 为每类任务指定默认模型与升级条件
4. 保留人工升级开关和自动升级规则
5. 记录每次调用的任务类型与成本，方便后续优化

## 7.1 适配器原则

LLM 接入必须做适配器层，不能让业务模块直接绑定某一个模型或某一家供应商。

目标：

- 支持多模型
- 支持多供应商
- 支持按任务切换
- 支持失败回退
- 支持后续替换供应商时不改业务逻辑

### 建议分层

推荐至少分成三层：

#### 第一层：任务层

由业务代码按“任务类型”发起调用，而不是按“某个厂商的某个模型”发起调用。

例如：

- `extract`
- `guided_question`
- `draft_stage`
- `final_polish`
- `root_cause_deep_analysis`

这一层只表达“我需要什么能力”，不表达“我用哪家模型”。

#### 第二层：路由层

由统一的模型路由器决定：

- 当前任务默认用哪个模型
- 当前任务默认走哪个供应商
- 是否需要自动升级
- 某个供应商失败时是否切换备用供应商

这一层负责策略，不负责具体 SDK 调用。

#### 第三层：Provider Adapter 层

每家供应商都实现同一套适配接口。

例如：

- `QwenAdapter`
- `DeepSeekAdapter`
- 未来其他国内 / 聚合供应商适配器

每个 adapter 负责：

- 请求格式转换
- 参数映射
- 响应解析
- 错误格式统一
- token / 成本元数据回传

### 业务层禁止直接做的事

以下做法应明确禁止：

- 在 `extractor`、`guided-thinking`、`report-builder` 里直接调用供应商 SDK
- 在业务逻辑里写死模型名
- 在业务逻辑里写死供应商特定参数
- 在多个模块里重复拼 prompt 调用代码

### 推荐接口方向

上层更适合调用类似这样的抽象接口：

- `runLlmTask(taskType, input, options)`

而不是：

- `callOpenAI(model, prompt)`
- `callAnthropic(model, prompt)`

前者面向业务任务，后者面向厂商细节。

### 这样做的价值

好处很直接：

- 后续可以同时接 OpenAI、Anthropic、Google 或国内聚合供应商
- 可以为不同任务选不同模型档位
- 可以逐步 A/B 测试不同供应商效果
- 可以按成本、速度、质量做路由策略
- 未来切换供应商时，不需要重写领域层和工作流层

## 7.2 当前推荐默认架构

对本项目，推荐的默认关系是：

- `workflow-engine / extractor / guided-thinking / report-builder`
  - 只依赖 `LLM Task Facade`
- `LLM Task Facade`
  - 只依赖 `Model Router`
- `Model Router`
  - 只依赖 `Provider Adapters`
- `Provider Adapters`
  - 才真正接供应商 SDK

这样可以把供应商变化限制在底层，不污染上层业务模块。

---

## 8. 当前结论

对这个产品来说，最贵的模型不应该成为默认底座。

更合理的做法是：

- 用便宜模型先覆盖所有用户输入的语义抽取
- 用规则守住字段校验、状态机和稳定结构
- 用 `qwen3.5-plus` 统一承担前两档任务
- 用 `deepseek-chat` 处理第三档默认高级任务
- 用 `deepseek-reasoner` 只解决真正高价值的复杂问题

这套策略更符合当前 demo 阶段，也更适合未来面向年轻工程师的个人付费模型。
