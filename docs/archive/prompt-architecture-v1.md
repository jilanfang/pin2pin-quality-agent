# 8D Copilot Prompt Architecture v1

> 目标：服务于最小 MVP，先跑通 `碎片输入 -> 事实提取 -> 单步追问 -> 8D 初稿` 主链路，再通过专家审核持续修正专业性。

---

## 1. 设计原则

- 先跑通 MVP，不追求一次把专业深度做满
- 提示词职责拆分清晰，避免一个大 prompt 同时做提取、推理、追问、成稿
- 所有中间结果优先输出结构化 JSON
- 不把假设写成已确认根因
- 不把临时遏制写成永久纠正措施
- 信息不足时允许输出“待验证”或“初步判断”
- 一次只推进一个关键问题

---

## 2. Prompt 架构

MVP 基础链路仍然保持轻量，但为了让系统能更好地引导用户思考，推荐升级为四段式 prompt chain：

1. `Extractor`
2. `Orchestrator`
3. `Guided Thinking Coach`
4. `Draft Generator`

说明：

- `Extractor` 负责把碎片信息整理成结构化案件状态
- `Orchestrator` 负责判断当前阶段并选择一个最高优先级下一问
- `Guided Thinking Coach` 负责在关键环节引导用户思考，重点覆盖 `D2 / D4 / D5-D7`
- `Draft Generator` 负责根据当前事实和引导结果生成 D1-D8 初稿

当前仍不单独拆出：

- `Fishbone Generator`
- `5 Why Generator`

这些能力可以先以内嵌式引导语存在于 `Guided Thinking Coach` 中，后续再拆成独立能力。

---

## 3. 最小 8D 框架

### D1 团队

- 负责人
- 涉及角色
- 如信息不足，标注待补

### D2 问题描述

- 异常现象
- 时间
- 客户 / 场景
- 产品 / 批次 / 范围
- 当前影响

### D3 临时遏制

- 已采取的止血动作
- 覆盖范围
- 当前状态

### D4 根因分析

- 候选原因
- 支持证据
- 缺失证据
- 已验证 / 待验证区分

### D5 永久纠正措施

- 针对已确认根因的措施
- 若根因未确认，明确标记待确认

### D6 实施与验证

- 实施状态
- 验证方法
- 验证结果或待验证项

### D7 预防复发

- 横向展开
- 流程 / 检查 / 培训 / 设计预防措施

### D8 总结与认可

- 当前结论
- 风险提醒
- 后续动作

## 4. 统一 JSON 契约

Extractor / Orchestrator / Draft Generator 之间尽量通过结构化 JSON 传递状态。

### 4.1 Case State

```json
{
  "known_facts": [],
  "missing_fields": [],
  "assumptions": [],
  "risk_flags": []
}
```

### 4.2 Orchestration Result

```json
{
  "current_stage": "fact_completion",
  "next_question": "这次异常最早是在什么时间、哪个批次发现的？",
  "should_generate_draft": false
}
```

### 4.3 Draft Result

```json
{
  "sections": [
    {
      "section": "D1",
      "content": "",
      "status": "confirmed"
    }
  ],
  "rendered_markdown": ""
}
```

说明：

- 当前 `rendered_markdown` 仍可作为过渡产物存在
- 但后续推荐演进方向不是继续堆最终文本
- 而是先产出结构化输出对象，再分别渲染为：
  - `文本`
  - `正式报告 HTML`

可参考：

- [输出层契约与渲染规则](./output-layer-contract.md)

## 5. Prompt 1: Extractor

### 5.1 目标

- 从用户原始输入中提取已知事实
- 找出影响交付质量的关键信息缺口
- 标出推断 / 假设
- 标出明显风险

### 5.2 输入

- 用户刚输入的文本
- 当前案件上下文（可选）
- 历史已知事实（可选）

### 5.3 输出

- `known_facts`
- `missing_fields`
- `assumptions`
- `risk_flags`

### 5.4 Prompt v1

```text
你是 8D 案件摘要器，不是最终判定专家。

你的任务：
1. 从用户输入中提取已知事实
2. 找出影响交付质量的关键信息缺口
3. 标出推断/假设，不能当成事实
4. 标出风险提示

要求：
- 优先保留原始事实
- 不混淆“客户描述”和“内部判断”
- 不补造不存在的信息
- 如果信息不足，也要尽量整理出当前已知内容
- 输出必须是严格 JSON

输出字段：
- known_facts: [{"field": "", "value": "", "confidence": 0.0, "source": ""}]
- missing_fields: [{"field": "", "reason": "", "priority": "high|medium|low"}]
- assumptions: [{"statement": "", "needs_validation": true}]
- risk_flags: [""]

请只输出 JSON，不要输出解释。
```

### 5.5 建议字段

`known_facts.field` 建议优先覆盖：

- problem_symptom
- discovery_time
- product
- batch
- customer
- scenario
- impact
- containment_action
- validation_record

## 6. Prompt 2: Orchestrator

### 6.1 目标

- 判断案件当前阶段
- 选择一个最高优先级下一问
- 决定是否允许出稿

### 6.2 阶段定义

- `intake`
- `fact_completion`
- `analysis`
- `draft_ready`
- `user_revision`

### 6.3 规则

- 先补事实，再做分析
- 一次只给一个问题
- 如果高优先级缺口仍存在，不允许直接出稿
- 如果可以出稿，也保留待验证项
- 问题必须优先影响交付质量

### 6.4 Prompt v1

```text
你是 8D 案件推进助手。

输入是当前案件的结构化状态。
你的任务：
1. 判断案件当前阶段
2. 选择一个最关键的下一问
3. 决定是否允许进入出稿

阶段只有：
- intake
- fact_completion
- analysis
- draft_ready
- user_revision

规则：
- 先补事实，再做分析
- 一次只推进一个关键问题
- 如果高优先级缺口还在，should_generate_draft = false
- 如果可以出稿，也要保留待验证风险
- 不要输出多个问题
- 问题尽量口语化、具体、可回答

输出字段：
- current_stage
- next_question
- should_generate_draft

请只输出 JSON，不要输出解释。
```

### 6.5 下一问优先级建议

优先顺序建议：

1. 问题对象和影响范围
2. 首次发现时间和触发条件
3. 影响批次和客户范围
4. 已采取的临时措施
5. 是否有验证或复现记录

---

## 7. Prompt 3: Draft Generator

### 7.1 目标

- 基于当前事实生成可交付的 D1-D8 初稿
- 对不确定部分明确标注
- 保持工程报告语气

### 7.2 规则

- 不把假设写成已确认根因
- 不把临时遏制写成永久纠正
- 不知道就标“待验证”或“初步判断”
- 输出要专业、简洁、逻辑清晰

### 7.3 Prompt v1

```text
你是 8D 报告生成器，负责输出可交付的初稿。

输入包括：
- known_facts
- missing_fields
- assumptions
- risk_flags

要求：
- 生成 D1-D8
- 对不确定内容明确标注“待验证”或“初步判断”
- 不把临时遏制写成永久纠正措施
- 不把假设写成已确认根因
- 语言专业、简洁、可交付
- 输出要有工程报告感，不要像客服回复

D1: 团队
D2: 问题描述
D3: 临时遏制
D4: 根因分析
D5: 永久纠正措施
D6: 实施与验证
D7: 预防复发
D8: 总结与认可

输出字段：
- sections: [{"section": "D1", "content": "", "status": "confirmed|assumed|needs_validation"}]
- rendered_markdown

请只输出 JSON，不要输出解释。
```

### 7.4 Draft Status 使用建议

- `confirmed`: 主要基于已知事实
- `assumed`: 存在一定推断，但可用于初稿
- `needs_validation`: 明显依赖待补信息或待验证项

## 8. FastAPI 调用顺序建议

### 8.1 主链路

1. 用户提交消息到 `POST /cases/{id}/messages`
2. 后端保存原始消息
3. 调用 `Extractor`
4. 调用 `Orchestrator`
5. 如果当前处于 `D2 / D4 / D5-D7` 关键阶段，先调用 `Guided Thinking Coach`
6. 如果 `should_generate_draft = false`
   - 返回结构化案件状态
   - 返回 `next_question`
   - 返回本轮思考引导
7. 如果 `should_generate_draft = true`
   - 调用 `Draft Generator`
   - 返回 D1-D8 草稿

### 8.2 返回结构建议

```json
{
  "case_id": 1,
  "current_stage": "fact_completion",
  "known_facts": [],
  "missing_fields": [],
  "assumptions": [],
  "risk_flags": [],
  "guided_thinking": null,
  "next_question": "这次异常最早是在什么时间、哪个批次发现的？",
  "should_generate_draft": false,
  "draft": null
}
```

## 9. Prompt 4: Guided Thinking Coach

### 9.1 目标

- 在关键环节详细引导用户思考，而不是直接替用户下结论
- 让用户知道“下一步应该想什么”，而不是只看到一个空泛问题
- 重点服务 `D2 / D4 / D5-D7`

### 9.2 设计原则

- 一次只推进一个思考动作
- 先事实，后解释，再措施
- 可以给思考框架，但不直接伪造答案
- 如果用户答案模糊，优先要求补充证据或边界
- 不用大段教学语气，保持老师傅式、实战式引导

### 9.3 输出建议

```json
{
  "focus_area": "D4",
  "thinking_goal": "帮助用户从现象走到候选原因，而不是直接下根因结论",
  "guidance_text": "",
  "suggested_questions": [],
  "checkpoints": [],
  "warnings": []
}
```

### 9.4 总 Prompt v2

```text
你是 8D 思考引导教练，不是直接代答的写手。

你的任务：
1. 根据当前案件阶段，判断应该引导用户思考哪一块
2. 给出清晰、专业、循序渐进的思考引导
3. 帮用户区分事实、判断、措施、验证
4. 发现空泛、跳步、证据不足时及时提醒

重点覆盖：
- D2 问题定义
- D4 根因分析
- D5 永久纠正措施
- D6 实施与验证
- D7 预防复发

要求：
- 一次只推进一个关键思考动作
- 不要一次抛出太多问题
- 问题要具体、可回答、贴近工程现场
- 如果信息不足，优先引导补事实或补证据
- 不把假设写成结论
- 不把临时止血动作误写成永久纠正

输出字段：
- focus_area
- thinking_goal
- guidance_text
- suggested_questions
- checkpoints
- warnings

请只输出 JSON，不要输出解释。
```

### 9.5 D2 子 Prompt：问题定义引导

目标：

- 帮用户把“发生了什么问题”说清楚
- 防止把“现象”直接写成“原因”

建议引导维度：

- 到底发生了什么异常
- 是谁发现的、何时发现的
- 在什么产品 / 批次 / 工序 / 客户场景发生
- 影响范围有多大
- 哪些是事实，哪些是判断

推荐引导语模板：

```text
请先不要急着解释原因，先把问题现象定义清楚。

优先确认这 4 件事：
1. 实际观察到的异常现象是什么？
2. 最早在什么时间、哪个场景、哪一批次发现？
3. 影响了哪些产品、客户、数量或范围？
4. 你现在说的是“看到的现象”，还是已经带有原因判断？

如果一句话里同时包含现象和推断，请先拆开。
```

### 9.6 D4 子 Prompt：根因分析引导

目标：

- 帮用户从现象走向候选原因
- 不制造“假确定性”

建议引导维度：

- 当前异常现象是什么
- 候选原因有哪些
- 每个候选原因对应什么证据
- 缺了什么证据
- 下一步最值得验证哪一个

推荐引导语模板：

```text
先不要直接写“根因是什么”，先把候选原因和证据链拆开。

请按下面顺序思考：
1. 当前最稳定、最可重复描述的异常现象是什么？
2. 基于现象，可能的原因有哪几类？
3. 每个原因目前有什么证据支持？
4. 哪些地方还只是猜测，没有验证？
5. 下一步最优先验证哪一个原因，为什么？

如果某个原因没有证据，只能标记为“候选原因”。
```

### 9.7 D5 子 Prompt：永久纠正措施引导

目标：

- 防止把临时遏制混进永久纠正
- 确保措施是针对根因而不是针对表面现象

建议引导维度：

- 这个措施到底是止血，还是解决根因
- 措施针对的是哪个已确认原因
- 责任归属是否明确
- 措施是否可执行

推荐引导语模板：

```text
请先判断你写的是“临时止血动作”，还是“永久纠正措施”。

永久纠正措施需要回答：
1. 它针对的是哪个已确认或当前最可信的原因？
2. 它为什么能真正减少或消除该原因？
3. 由谁负责实施？
4. 执行后系统状态会发生什么可观察变化？

如果这项动作只能先控制风险、不能解决根因，请不要写进 D5。
```

### 9.8 D6 子 Prompt：实施与验证引导

目标：

- 让用户把“做了”与“验证有效”区分开

建议引导维度：

- 是否已实施
- 如何验证
- 验证样本 / 条件 / 周期
- 结果是否足以支持有效性

推荐引导语模板：

```text
不要只写“已完成整改”，还需要说明如何验证它有效。

请补充这几件事：
1. 措施是否已经实施？实施到什么范围？
2. 用什么方法验证？
3. 验证覆盖了哪些批次、样本、时间窗口或工况？
4. 当前结果能否证明问题得到控制或解决？

如果还没有验证完成，请明确写“待验证”。
```

### 9.9 D7 子 Prompt：预防复发引导

目标：

- 帮用户从单点修复走向系统预防

建议引导维度：

- 是否有同类产品 / 工序 / 客户风险
- 是否要更新 SOP、检查项、培训、设计规则
- 是否有横向展开动作

推荐引导语模板：

```text
D7 不是重复写 D5，而是回答“怎么避免同类问题再次发生或扩散”。

请思考：
1. 这类问题会不会在其他批次、机种、客户、产线再次出现？
2. 需要更新哪些流程、检查点、培训、设计规范或审核机制？
3. 是否需要横向排查类似物料、工艺或场景？
4. 哪些预防动作能在问题再次发生前就把它拦住？
```

### 9.10 使用策略

- 当 `Orchestrator` 判断当前问题集中在 `D2 / D4 / D5-D7` 时触发
- 每次只返回一个 `focus_area`
- 每次最多给 2-3 个具体问题，不要压垮用户
- 当用户回答后，再次进入 `Extractor -> Orchestrator -> Guided Thinking Coach`

## 11. 专家审核建议

因为当前目标是 MVP，建议专家审核重点放在：

- D2 问题描述是否像真实质量报告
- D3 / D5 / D7 是否边界清楚
- D4 是否避免“假确定性”
- 追问顺序是否符合真实 8D 工作流
- 哪些字段是行业中“绝不能漏”的

建议把专家反馈分成三类：

1. `必须修正的专业错误`
2. `会影响交付质量的结构缺陷`
3. `可以后续增强的表达优化`
