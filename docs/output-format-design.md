# 失效分析输出格式与文风设计

## 1. 文档目的

这份文档定义当前 `失效分析 / 异常响应工具` 的输出策略。

它重点解决四个问题：

1. 用户最终应该拿到什么格式的结果
2. 文风是否需要可选，应该怎么收敛
3. `文本` 与 `正式报告` 如何并存
4. HTML 与 PDF 在当前阶段和后续阶段分别怎么处理

## 2. 当前结论

当前阶段采用：

`三类结果 + 轻量文风可选 + 单一 HTML 风格 + HTML 转 PDF`

也就是：

- 输出同时支持：
  - `分析摘要`
  - `快速响应版`
  - `8D 正式报告`
- 文风支持轻量可选，但不做复杂配置
- `正式报告` 当前只做一套 HTML 风格
- PDF 不单独设计编辑模式，而是走 `HTML -> PDF`

## 3. 为什么不是只做一种输出

如果只做 `分析摘要`：

- 实现简单
- 但对客户交付和正式关闭的支撑不够强

如果只做 `8D 正式报告`：

- 看起来更完整
- 但很多用户最后还是要往自己公司的模板里贴
- 会损失可复制、可二次加工的灵活性

所以当前最合理的是：

- `分析摘要` 解决“先形成可信结论”
- `快速响应版` 解决“高压场景先交差、先封堵客户问题”
- `8D 正式报告` 解决“正式客户交付与闭环”

## 2.1 2026-03-24 新规则

- 产品主定位是 `失效分析工具`
- `8D` 是正式输出物之一，不再是唯一中心对象
- `快速响应版` 不是和 `8D 正式报告` 对立的独立入口
- 用户一开始不需要先决定自己要哪一种报告
- 同一案件推进过程中，系统根据成熟度与业务压力，逐步判断当前适合：
  - `分析摘要`
  - `快速响应版`
  - `8D 正式报告`
- 当案件止于 `D4` 时，默认先输出 `分析摘要`
- 用户明确需要正式交付稿时，再输出 `D4 截止版 8D`
- `D4 截止版 8D` 中 `D5-D8` 仍保留标题，但标注“当前不适用”
- 当前实现里如仍存在 `initial_24h` 这类命名，只视为历史内部枚举，不作为产品对外表述

## 4. 输出对象定义

## 4.1 输出一：文本

在产品 UI 中就叫：

`文本`

不要向用户强调 `Markdown` 这个词。

虽然底层可以用 Markdown 结构化生成，但对用户来说，它就是：

- 一份结构化文本
- 可以直接复制
- 可以粘贴到公司模板、邮件、Word、企业微信、客户回复框

### 文本输出的角色

- 作为最通用、最灵活的输出层
- 作为用户继续加工的基础材料
- 作为公司已有模板的内容来源

### 文本输出的要求

- 标题结构清楚
- 段落适合复制
- 不依赖复杂样式才能理解
- 保留事实、措施、待验证项的分层
- 不能为了好看牺牲可编辑性

## 4.2 输出二：正式报告

在产品 UI 中叫：

`正式报告`

它的本质是：

- 一份渲染好的 HTML 报告
- 比“文本”更像可交付成品
- 更适合直接预览、演示、导出 PDF

### 正式报告的角色

- 提升专业感与交付感
- 让年轻工程师更敢拿出去给同事、老板或客户看
- 为后续的 PDF 导出和模板付费能力铺路

### 正式报告的要求

- 视觉上要稳重、专业、不过度设计
- 适合中文工程报告语境
- 明确显示章节、状态和边界
- 对 `待验证 / 假设 / Open` 等状态有清楚表达

## 5. 文风设计

## 5.1 为什么需要文风

同一份事实内容，在不同交付对象面前，表达方式应该不同。

例如：

- 对客户要更谨慎
- 对内部协作可以更直接
- 对新人默认需要更稳妥的专业表达

所以文风是有价值的，但当前阶段不应该做得太重。

## 5.2 当前阶段文风方案

首版支持三档文风：

### 一：专业克制

这是默认档。

适合：

- 大多数国内客户场景
- 内部汇报
- 普通异常处理

特点：

- 专业
- 稳妥
- 不夸张
- 不太硬，也不太官话

### 二：对客正式

适合：

- 客诉回复
- 停线事件
- 需要更正式外发的文稿

特点：

- 更书面
- 更谨慎
- 更强调边界和风险控制
- 更避免情绪化或口语化表达

### 三：内部直给

适合：

- 内部异常流转
- 跨部门同步
- 研发 / PE / QE 快速对齐

特点：

- 更直接
- 更工程化
- 更强调问题、证据、动作项
- 减少对外话术感

## 5.3 文风的边界

文风只允许影响：

- 语气
- 句子组织
- 段落表达方式
- 正式程度

文风不允许影响：

- 事实本身
- 证据成熟度
- 风险等级
- 结案状态
- 是否属于已验证根因

也就是说：

`对客正式` 不等于可以把“待验证”写成“已确认”。

## 6. 当前推荐的输出组合

当前产品默认应提供：

- 一份 `文本`
- 一份 `正式报告`

并允许用户切换文风。

推荐默认组合是：

- 文风默认：`专业克制`
- 输出默认先展示：`文本`
- 用户一键切换到：`正式报告`

这样安排的原因：

- `文本` 更适合继续编辑和复制
- `正式报告` 更适合建立交付信心

## 7. HTML 设计方向

## 7.1 当前阶段只做一套风格

当前不要做多套皮肤。

只做一套：

`简洁正式的中文工程报告风格`

原因：

- 当前重点不是视觉花样，而是交付可信度
- 一套风格更容易统一质量
- 后续再把多风格作为付费点更合理

## 7.2 当前 HTML 风格应具备的特征

- A4 报告感
- 中文排版友好
- 标题层级清楚
- D1-D8 结构稳定
- 重点字段突出：
  - 客户
  - 产品
  - 工单 / 批次
  - 严重度
  - 案件状态
- `待验证`、`假设`、`Open` 这类状态要有明确视觉区分

## 7.3 当前 HTML 风格不应做的事

- 不要做花哨营销风
- 不要做重色块海报风
- 不要做过强品牌视觉
- 不要为了好看牺牲打印可读性

## 8. PDF 路径

## 8.1 当前阶段定位

PDF 不是一个独立编辑模式。

当前推荐路径：

`结构化内容 -> HTML 渲染 -> PDF 导出`

这样做的好处：

- 一份内容源支持多种交付
- HTML 和 PDF 的样式更容易统一
- 实现成本低于单独维护一套 PDF 模板逻辑

## 8.2 对产品的要求

为了支持未来 PDF，当前 HTML 就要有这些前提：

- 打印样式可控
- 页眉页脚逻辑可扩展
- 章节分页不会乱
- 中文排版和表格排版稳定

## 8.3 当前阶段不做什么

当前不做：

- 多公司模板导入
- 多品牌皮肤
- 高自由度模板编辑器
- 用户自定义 PDF 版式系统

这些都应该后置。

## 9. 产品交互建议

## 9.1 用户视角的命名

不要用太技术的名字。

推荐叫法：

- `文本`
- `正式报告`
- `文风`

避免叫法：

- `Markdown`
- `HTML 模板`
- `导出视图引擎`

## 9.2 交互顺序建议

建议顺序：

1. 用户先拿到 `文本`
2. 系统提示可切换为 `正式报告`
3. 用户选择文风
4. 用户预览正式报告
5. 后续再支持导出 PDF

这样用户更容易理解：

- 文本是底稿
- 正式报告是成品视图

## 9.3 默认策略

在国内客户场景下，默认应为：

- 输出语言：中文
- 文风：`专业克制`
- 首屏结果：`文本`
- 次级切换：`正式报告`

## 10. 对当前产品规则的影响

这套设计会直接影响生成逻辑。

## 10.1 生成逻辑要先有“内容层”

内容层应先独立产出：

- 标题
- 案件摘要
- D1-D8 内容
- 状态标签
- 风险标签
- 待验证项

然后再映射到：

- 文本
- 正式报告

不能反过来让 UI 样式驱动内容结构。

## 10.2 文风应是生成参数，不是内容分叉

推荐把文风看成一组表达参数，而不是三套完全不同的模板。

这样可以避免：

- 方法论走样
- 证据标签丢失
- 不同文风之间内容结构不一致

## 10.3 证据状态必须跨输出一致

无论是 `文本` 还是 `正式报告`，下面这些状态必须一致：

- 已知事实
- 假设
- 待验证
- 已验证措施
- Open / Closed

不能出现：

- 文本里写 `待验证`
- 正式报告里为了好看就写成 `已确认`

## 11. 当前不做，但要记住的未来付费方向

未来比较自然的付费扩展点包括：

- 多种正式报告风格
- 行业模板
- 客户模板适配
- 公司 Logo / 品牌化
- PDF 高级导出
- Word 模板映射

这些都适合以后做，而不是现在做重。

## 12. 当前阶段的一句话结论

当前阶段最合理的输出策略是：

`默认中文专业克制文风 + 文本/正式报告双输出 + 单一 HTML 风格 + HTML 转 PDF`

这套方案能同时满足：

- 年轻工程师需要快速交付
- 用户仍要适配公司模板
- 产品后续可以自然扩展付费输出能力

补充要求：

- 后续实现必须采用：
  - `内容层 -> 文风层 -> 渲染层`
  - 不能把 HTML、PDF 或文风直接揉进方法论判断里
