# 8D Copilot 专家审核清单（电子质量工程 MVP v1）

> 目的：用于请资深电子/硬件质量工程专家审核当前 MVP 的专业性边界，判断这套 `碎片输入 -> 追问 -> 8D 初稿` 是否足够像真实一线质量工程助理，而不是通用文书生成器。

---

## 1. 审核定位

请以以下角色视角审阅：

- 客诉质量工程师（CQE）
- 制造质量工程师（MQE / PQE）
- 供应商质量工程师（SQE）
- 可靠性 / 失效分析工程师（Reliability / FA）
- 电子硬件研发质量或 NPI 质量工程师

请重点判断：

1. 这是不是一个“会推进案件”的助手，而不是只会润色文本的工具
2. 这套追问顺序是否符合电子工程 8D 的真实工作流
3. 这份初稿是否具备真实工程语感
4. 哪些专业缺口会让一线工程师立刻觉得“不像业内的人写的”

---

## 2. MVP 审核范围

当前版本只审核最小链路，不要求一次覆盖完整企业级能力。

当前范围：

- 用户输入碎片化案件信息
- 系统提取已知事实
- 系统识别高优先级缺口
- 系统一次只追问一个关键问题
- 系统生成可修改的 D1-D8 初稿
- 初稿明确区分事实、假设、待验证项

当前不在本轮强制范围：

- 相似案例召回
- 自动鱼骨图 / 5 Why 图形化输出
- 多人协作审批流
- ERP / MES / PLM / QMS 对接
- 真正行业细分模板（如电源、射频、模组、封测独立模板）

---

## 3. 总体验收问题

请先给出总体判断：

- 这版是否达到“可给真实质量工程师试用”的最低门槛
- 这版最像业内工具的地方是什么
- 这版最不像业内工具的地方是什么
- 如果只能优先修 3 个问题，应该先修哪 3 个

建议评级：

- `A`：已具备明显行业感，可进入小范围试用
- `B`：方向对，但仍有几处关键专业缺口
- `C`：结构还行，但行业感弱，容易像通用 AI
- `D`：不建议给真实工程师试用

---

## 4. 接案 / 信息补全审核

### 4.1 已知事实提取是否像电子质量工程师

请判断系统是否优先识别这些关键信息：

- 异常现象本身
- 产品型号 / 料号 / 机种
- 批次 / Lot / Date Code
- 工单 / 线别 / 站位 / 工序
- 客户 / 市场 / 应用场景
- 首次发现时间
- 当前影响范围（出货 / 库存 / 在制 / 客户现场）
- 已有遏制动作
- 已有验证记录

请指出：

- 哪些字段优先级排序合理
- 哪些字段在电子场景里明显缺失
- 哪些字段应该合并
- 哪些字段应该拆开

### 4.2 单问题追问是否合理

请判断系统“一次只问一个关键问题”的策略是否合理：

- 是否优先问最影响交付风险的问题
- 是否避免在事实不足时直接追问根因
- 是否避免一次抛出太多问题
- 是否符合真实工程师补案习惯

请特别判断追问顺序是否合理：

1. 异常对象与范围
2. 首次发现时间与触发条件
3. 批次 / Date Code / 线别 / 工位
4. 影响客户 / 出货 / 库存 / 在制范围
5. 已采取的临时遏制
6. 是否有复现与验证记录

---

## 5. D2 问题定义审核

请重点判断 D2 是否达到真实工程案件最低要求。

### 检查点

- 是否区分“客户投诉现象”和“内部复现现象”
- 是否写清发现时间、地点、阶段
- 是否写清产品、批次、数量、客户影响
- 是否避免把原因猜测写进问题描述
- 是否具有可复述性，而不是空话

### 电子工程特别关注

- 是否应增加 Date Code / Lot No. / 物料版本 / 固件版本
- 是否应增加测试站点（ICT / FCT / ATE / Burn-in / OQC）
- 是否应增加失效比例、样本数、失效率表达方式
- 是否应增加发生条件（温度、电压、负载、时间、工况）

请指出当前 D2 草稿最容易显得外行的地方。

---

## 6. D3 临时遏制审核

请判断 D3 是否体现真实质量工程“先止血”的思路。

### 检查点

- 是否区分临时遏制与永久措施
- 是否考虑在制品、库存、已出货、客户端四个范围
- 是否体现隔离、暂停、加严筛选、100% 检验、风险通知等动作
- 是否体现动作责任人与状态
- 是否避免写成泛泛的“加强管理”

### 电子工程特别关注

- 是否需要区分厂内遏制与客户端遏制
- 是否需要体现返工、复判、加测、替代料冻结等动作
- 是否需要体现批次追溯、序列号追溯、WIP/FG 库存控制

---

## 7. D4 根因分析审核

这是最关键的专家审核部分。

### 检查点

- 是否明确区分候选原因、已确认根因、待验证项
- 是否避免“看起来像根因，实际上没有证据”
- 是否体现证据链，而不是只有结论
- 是否能提示用户继续补验证而不是直接拍板
- 是否符合电子失效分析常见表达

### 电子工程特别关注

请判断系统是否应该更明确地区分以下层次：

1. 异常现象  
2. 失效部位  
3. 失效机理  
4. 诱因 / 控制失效点  
5. 系统性根因

请补充判断是否需要提示这些验证方式：

- 复现试验
- 样本对比
- 换料 / 换机 / 换线验证
- 参数回看
- AOI / X-Ray / 显微镜 / 切片 / 截面
- 电性能测试
- 老化 / 环境应力 / 可靠性试验
- 日志 / 程序版本 / 治具版本核对

请指出：

- 当前 D4 提示最不足的 3 点
- 哪些表述会让工程师觉得“像 AI 在瞎猜”

---

## 8. D5-D6 措施与验证审核

请判断 D5 / D6 是否具备“措施闭环”意识。

### 检查点

- 永久措施是否直接对应已确认根因
- 是否避免根因未确认就直接给永久措施
- 是否写清实施对象、时间、责任人
- 是否写清验证方法、样本量、通过标准
- 是否区分“措施已执行”与“措施已验证有效”

### 电子工程特别关注

- 是否需要增加首件 / 小批 / 批量验证层级
- 是否需要增加 DOE、比对样、回归测试、可靠性验证
- 是否需要增加制程参数窗口确认、治具校验、程序版本固化
- 是否需要增加供应商来料验证与替代料验证

---

## 9. D7 预防复发审核

请判断 D7 是否体现电子制造现场的“横向展开”意识。

### 检查点

- 是否考虑相邻料号、共线机种、同供应商批次
- 是否考虑同工艺窗口、同设备、同治具、同程序版本
- 是否体现文件更新、检查项更新、培训、设计规则更新
- 是否避免只写“加强培训”

### 电子工程特别关注

- 是否需要增加 PFMEA / Control Plan / SOP / SIP 更新
- 是否需要增加 ECN / 软件版本 / BOM / AVL 管控
- 是否需要增加关键参数监控和报警阈值

---

## 10. 8D 文风审核

请从真实工程报告语感判断：

- 是否像质量工程师写的，而不是客服或市场文案
- 是否够简洁、克制、可交付
- 是否避免空话、套话、无证据判断
- 是否适合后续继续补充和评审

请特别指出：

- 哪些措辞像“通用 AI”
- 哪些措辞更像“资深质量工程师”

---

## 11. 输出元信息审核

当前系统会输出以下元信息，请判断是否有助于专家审阅：

- `source`: `llm` / `fallback`
- `prompt_version`
- `domain_profile`
- `review_mode`

请判断：

- 这些元信息是否足够帮助审核当前草稿可信度
- 是否还需要增加 `industry_template`、`failure_category`、`confidence_band`

## 13. 当前版本审核目标

本轮不是要证明系统已经专业完善，而是要确认：

- 方向是不是对的
- 追问顺序是否基本合理
- 8D 草稿是否具有电子质量工程的最低行业感
- 下一轮应优先补“专业性”还是“交互流程”
