# Fireline GTM Execution

## 目标

让 `/Users/jilanfang/ai-quality` 不只是产品仓库，也成为当前 GTM 主战场的执行 source of truth。

一句话：

`Pin2pin Fireline` 当前要先把异常响应 / 客诉 / 8D 这条收入路径打穿。

---

## 当前定位

当前产品主定位已经升级为：

1. 异常响应工具
2. 失效分析工具
3. `8D` 是正式输出物之一，但不是唯一中心对象

当前 GTM 不应该把它讲成：

1. 大而全质量管理平台
2. 纯 8D 自动生成器
3. 制造业 AI 平台

更适合的讲法是：

`先帮大家把异常响应里最乱、最容易把人搞崩的那一段理顺。`

---

## GTM 主线

当前主线固定成：

1. 内容收 case
2. case 带来试用和私聊
3. 复杂 case 进入项目型支援
4. 高频用户进入标准化产品
5. 真实反馈继续反哺产品

```text
内容 / 评论区 / FFF
        |
      收 case
        |
   试用 / case 门诊
        |
项目型支援 or 标准化试用
        |
  产品反馈 / 案例沉淀
```

---

## In Scope

### 1. Case 门诊机制

要把“欢迎扔 case”从一句话变成固定机制。

至少要做：

1. 所有内容结尾征集 case
2. 每周拆 1 个公开案例
3. 复杂现场优先进入深聊
4. 收到的高价值 case 要能沉淀为产品问题和内容选题

### 2. 项目型收入包装

把轻服务包装讲清楚。

建议对外只讲 3 种：

1. 异常响应支援
2. 8D 首版加速
3. RCA / CAPA 协作推进

### 3. 标准化试用承接

不是所有人都走项目型。

需要保留标准化试用入口，适合：

1. 年轻质量工程师
2. 高频写首版 / 写对外回复的人
3. 愿意自己先跑真实 case 的个人用户

### 4. 内容-产品联动

每周至少回答这 3 个问题：

1. 这周收到了哪些真 case
2. 哪些问题是表达问题，哪些是产品问题
3. 哪些案例值得变成演示种子案例或产品 benchmark

---

## Not In Scope

1. 讲平台级大故事
2. 让 `Atlas` 出现在公开 GTM 主线里
3. 为了 GTM 再重新发明一套与产品脱离的故事
4. 只做内容，不接 case

## 具体任务

### 任务 1：固定产品对外一句话

要求：

1. 所有对外说法统一
2. 不回到旧的“纯 8D 工具”表达
3. 也不飘到“全流程质量平台”

### 任务 2：固定 case 征集机制

要求：

1. 公众号、小红书、知乎结尾统一征集 case
2. 评论区互动目标统一改成接 case
3. 有离谱 case 的人能很快被承接到私聊或试用

### 任务 3：固定案例栏目

栏目分两层：

1. `公开案例拆解`
2. `本周最离谱质量 case`

先用公开资料和典型案例垫底，再逐步切到真实匿名 case。

### 任务 4：固定项目型收入说法

要求：

1. 不是卖咨询公司
2. 是轻量支援
3. 用来补现金流、补案例、补产品认知

### 任务 5：固定 FFF 节奏

两个人每周都做：

1. 联系人
2. 聊 case
3. 接反馈

不要把 GTM 误解成纯内容运营。

---

## 完成标准

1. `Fireline` 对外说法统一
2. 每周稳定收 case
3. 内容和 case 门诊形成固定 loop
4. 标准化试用和项目型支援两条承接路径都能跑

---

## 触发条件

### 继续加码 Fireline GTM

满足任意两条，就继续加码：

1. 稳定拿到真实 case
2. case 能转成试用或深聊
3. 项目型支援开始出现强需求
4. 个人用户开始表现出真实重复使用

### 触发 GTM 调整

满足任意两条，就重新 review：

1. case 数量少但泛咨询多
2. 试用多、继续用少
3. 内容有热度但没有高质量现场输入
4. 项目型支援需求很强，但标准化产品承接明显跟不上

## 项目接口

### 输入

来自官网：

1. 试用线索
2. case 线索
3. 项目型支援咨询

来自公司层：

1. `Fireline-first` 总规则
2. investor / partner narrative 分离规则

### 输出

`Fireline` 要向外输出：

1. 更强的产品说法
2. 更强的 case 门诊机制
3. 更清楚的项目型支援包装

`Fireline` 要向公司层回流：

1. 真实案例
2. 有效文案
3. 用户原话
4. 收入与复购信号

## 风险地图

### 最大风险

1. 内容越做越像媒体，不像获客和收 case
2. 项目型支援做重，稀释标准化产品
3. 标准化产品过轻，承接不住真实现场
4. 评论区和私聊只停留在“讨论”，没有进入试用或项目型支援

### 反向约束

1. 所有内容都必须能回到 case
2. 所有评论区互动都以接 case 为目标，不以推产品为目标
3. 不把 `Fireline` 写成大平台
4. 不把项目型支援写成大咨询

---

## 成功 / 失败判据

### 成功信号

1. 用户开始主动丢 case
2. case 能转成试用、深聊或项目型支援
3. 试用里开始出现重复使用或团队扩散
4. 真实案例开始反哺产品迭代

### 失败信号

1. case 只停留在围观层
2. 项目型支援没有形成明确需求
3. 试用用户不愿意带真实现场来
4. 大家觉得内容有意思，但不愿意真的把事情交给 Fireline

---

## 时间窗口

当前 GTM loop 至少连续跑 `6` 周后再做大调整。

前 `6` 周主要验证：

1. 能不能稳定收 case
2. 能不能让 case 转成试用 / 深聊
3. 哪一类 case 最值得产品化

---

## 资源预算

Fireline 当前 GTM 投入优先级固定：

1. 收 case
2. 接 case
3. 试用承接
4. 项目型支援
5. 内容放大

如果时间不够，优先砍：

1. 多平台扩张
2. 漂亮但低转化的内容包装
3. 泛品牌内容

---

## 资产沉淀规则

每周至少沉淀：

1. 真实用户原话
2. 真实案例摘要
3. 最有效标题和文案
4. 最值得做成 seed case / benchmark 的现场

不要沉淀：

1. 没有具体背景的泛吐槽
2. 没法反哺产品或内容的噪音反馈

---

## 复盘节奏

### 每周

看：

1. 新 case 数
2. 深聊数
3. 试用推进数
4. 项目型支援推进数

### 每 4 周

看：

1. 标准化试用与项目型支援的比例是否健康
2. 哪个 case 类型最值钱
3. 当前产品边界是否还对
